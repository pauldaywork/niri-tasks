# Up Next — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An "Up next" action tags a task as the one to do next. Its task card's icon and text turn yellow, and the card sorts directly under the active tasks. Nothing else about the task changes.

**Architecture:** Up next is Taskwarrior's own `+next` tag. `src/task.rs` gets the tag constant, `Task::is_up_next()`, `set_up_next()` (one `task modify +next`/`-next`), and `up_next_label()`, which gives the toggle's words ("Up next" or "Not up next") to the CLI notification, the fuzzel menu and the panel button alike. `niritasks task up-next <uuid>` toggles it. The action menu and a new `Action::UpNext` button on the panel's action row both run that command. The panel's `cards()` sorts up next second, after active and before urgency. A card that shows up next gets an `up-next` CSS class, coloured Catppuccin yellow `#f9e2af`.

**Tech Stack:** Rust 2021, clap derive, GTK4 (gtk4-rs) CSS, Taskwarrior 2.6 CLI. No new crates.

**Spec:** Taskwarrior task `f4b4cb6c-f962-4a34-aa99-235919703e01`. Read it with `task rc.json.array=on f4b4cb6c-f962-4a34-aa99-235919703e01 export`. Its description and notes are the spec.

## Global Constraints

- The tag is Taskwarrior's own `next`, kept as a constant (`UP_NEXT_TAG`) beside `PLANNED_TAG` in `src/task.rs`, with `Task::is_up_next()`.
- The action toggles. It adds `+next`, or removes it from a task already up next. Its words are "Up next" / "Not up next". It never touches status, start, wait, other tags or notes.
- Starting a task keeps the tag. An active card stays green, and a waiting card keeps its Waiting look. Yellow shows on every other card, including the blocked lock and the planned dot.
- The yellow is Catppuccin's `#f9e2af`, the Edit button's colour, kept as an `UP_NEXT` constant in `src/panel/style.rs`.
- It is offered in the action menu, as an action row button (not on waiting cards or "+N more"), and as `niritasks task up-next <uuid>`. All three run the same command.
- No extra code for the picker (`src/rows.rs`) or `task next`. Taskwarrior's `urgency.next.coefficient` (15) already lifts a `+next` task there.
- Out of scope: an Up next filter tab, a special marker in the fuzzel picker, and a keyboard letter for the button. The spec names none, and Speak has none either.
- Done when: an up next task's card shows yellow directly under the active cards, and pressing the action again clears it. The command, the menu entry and the button all toggle it. Tests cover the sort, the CSS rule and the button list, and `bash tests/all.sh` passes.
- House style: every item gets a doc comment that says *why*, in the plain voice of the surrounding code. Commits use Conventional Commits (`feat(scope): …`, imperative, lowercase, ≤72 chars). End each with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Decisions made while planning (flag any you disagree with)

- **Where it sits.** In the menu it comes after Speak: Edit, Note, Speak, Up next, Refine, …. On the action row it also comes after Speak: … Edit, Speak, Up next, Stop, Waiting, Remove.
- **Icon.** Font Awesome's bookmark, `\u{f02e}`, from the same Nerd Font as the other buttons.
- **Button behaviour.** The panel keeps the keyboard, as it does for Speak, Waiting and Remove, because Up next opens nothing. The card does not leave the list. It only moves position on the next tick, and `render()` puts the focus back on it by widget name.
- **Words on an up next card.** The button's tooltip and hint read "Not up next", the same as the menu entry for that task.
- **Notification.** `task up-next` notifies "Up next: <description>" or "Not up next: <description>", using the words that were picked. This follows how `apply_status` notifies "Completed: …".
- **Sort among active tasks.** Active comes first, then up next, then urgency. So an active up next task leads the active ones. The spec only asks for "under the active tasks", and this is the simplest key order.
- **Who decides yellow.** The model does: `Card::shows_up_next()` is false on Active and Waiting cards, and the surface adds the class only when it is true. One CSS rule, placed after the dimmed `.blocked` rule, then beats the dimming on a blocked card.

```rust
/// What the action menu and the action row call the up next toggle on a

/// `niritasks task up-next` notifies.
pub fn up_next_label(up_next: bool) -> &'static str {

/// Put the up next tag on a task, or take it off. Only the tag changes:
/// `+next` or `-next` goes as one argument of its own, so taskwarrior reads
/// it as a tag and not as words for the description, and the task's status,
/// start, wait, other tags and notes stay as they were. A started task stays
/// started.
pub fn set_up_next(uuid: &str, on: bool) -> Result<()> {
    let sign = if on { '+' } else { '-' };
    let status = base()
        .arg(uuid)
        .arg("modify")
        .arg(format!("{sign}{UP_NEXT_TAG}"))
        .status()
        .context("could not run `task modify`")?;
    anyhow::ensure!(status.success(), "`task modify {sign}{UP_NEXT_TAG}` failed");
    Ok(())
}
```

Replace `cards`' doc comment and its sort with:

```rust
/// The task cards for one workspace tag, every one of them: the active task
/// first, then the up next ones, then the rest most urgent first.
///
/// Active first even when something else is more urgent: it is the work in
/// progress, and the one card worth reading without hovering. Up next comes
/// right under it, being the one to do next; its `+next` already adds
/// urgency, and this keeps it there whatever else outranks it. Being started
/// outranks being blocked, since you started it anyway. Blocked outranks
/// planned: a plan does not make a task you cannot start yet startable.
pub fn cards(tasks: &[Task], blocked: &[String]) -> Vec<Card> {
    let mut sorted: Vec<&Task> = tasks.iter().collect();
    sorted.sort_by(|a, b| {
```
